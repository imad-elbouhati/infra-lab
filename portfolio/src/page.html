Case 01/ Go · Kubernetes operator/ kubeguard-operator

A controller that keeps every Deployment inside policy

KubeGuard is a Kubernetes operator that continuously enforces replica, CPU, memory and label guardrails across a cluster — and corrects the resources that drift out of them.

View repository → Read the reconciler →
Problem

Once more than a handful of teams are pushing manifests, keeping every Deployment within sane bounds stops being a review problem and becomes an enforcement problem. Replica counts creep, resource limits get omitted or inflated, and ownership labels go missing — so cost attribution and capacity planning quietly degrade.

Context

Built as a standalone operator with Kubebuilder v4 and controller-runtime, targeting any Kubernetes cluster from v1.11.3 upward. The whole guardrail is expressed as one cluster-scoped custom resource, GuardPolicy, so platform teams declare policy once instead of reviewing it per manifest.

Architecture
  • Custom resource. GuardPolicy carries a namespaceSelector, maxReplicas, maxCPU, maxMemory and an enforceLabels map. No selector means the policy applies cluster-wide.
  • Dual-trigger reconciliation. The controller watches GuardPolicy objects and Deployments. A map function resolves any Deployment event back to the set of policies whose namespace selector matches, so a violating change is corrected on write rather than on the next sweep.
  • Continuous sweep. Every reconcile returns RequeueAfter: 5 * time.Minute, so drift introduced while the controller was down still gets caught.
  • Detect, then correct. detectDrift() produces a DriftReport — per-container CPU and memory targets, missing labels, a replica target — which correctDeployment() applies as a patch. Detection is pure and independently testable; mutation is isolated.
  • Reporting. Corrections are written to status.violations, summarised in a Reconciled status condition, and emitted as Kubernetes Events.
Technologies
Go 1.23Kubebuilder v4 controller-runtimeCRD / apiextensions KustomizeGinkgo + Gomega envtestGitHub Actions golangci-lintdistroless Prometheus ServiceMonitor
Engineering decisions
  • Typed quantities over strings. maxCPU and maxMemory are resource.Quantity, so the API server rejects malformed units at admission and comparisons use Cmp() rather than string parsing.
  • Merge patch, not update. Corrections go through client.MergeFrom(deployment) against a DeepCopy. Using Update() would send the whole object and lose concurrent writes from other controllers on a stale resourceVersion.
  • Auditability by default. Every corrected Deployment is stamped with platform.demo/last-corrected and platform.demo/corrected-by, so the next engineer to open the manifest can see what changed it and when — the question every mutating controller must be able to answer.
  • Operator ergonomics. The CRD declares the short name gp and printer columns, so kubectl get gp shows limits and age without a JSONPath incantation.
  • Least privilege at runtime. The manager ships on distroless/static:nonroot as UID 65532, with allowPrivilegeEscalation: false, all capabilities dropped and a RuntimeDefault seccomp profile — it satisfies the restricted Pod Security Standard.
Hardest part

Mapping a Deployment event back to the policies that govern it. A Deployment doesn't know which GuardPolicy applies to it — the relationship lives in a label selector on its namespace. deploymentToGuardPolicies() lists every policy, evaluates each one's namespace selector against the Deployment's namespace, and enqueues only the matching policies. Without that indirection the controller would either re-scan the entire cluster on every Deployment write, or miss policies entirely.

The second is a design question rather than a coding one: enforcement is reconcile-based, not admission-based. That choice is deliberate and it has a cost — see the trade-off below.

Implementation
// correctDeployment — patch, never overwrite
corrected := deployment.DeepCopy()

// ... clamp replicas, limits, inject labels ...

corrected.Annotations["platform.demo/last-corrected"] =
    time.Now().Format(time.RFC3339)
corrected.Annotations["platform.demo/corrected-by"] = policy.Name

if err := r.Patch(ctx, corrected, client.MergeFrom(deployment)); err != nil {
    return fmt.Errorf("failed to patch deployment: %w", err)
}
internal/controller/guardpolicy_controller.go
Result

Applying a GuardPolicy clamps over-provisioned Deployments back to the declared ceilings, injects any required ownership labels, and records what it changed. Operators see the outcome through kubectl get gp and kubectl describe rather than by reading controller logs.

The repository ships three GitHub Actions workflows — lint, unit tests and an end-to-end suite. The e2e suite deploys the controller into a real cluster under the restricted Pod Security Standard, verifies the manager pod runs, then authenticates against the metrics endpoint with a service-account token and asserts that controller-runtime metrics are actually being served.

Trade-off
Known limitation — stated deliberately Because enforcement runs in a reconcile loop rather than a validating admission webhook, a non-compliant Deployment is admitted first and corrected shortly after, not rejected outright. For guardrails that must never be breached even briefly, the next step is a validating webhook backed by the same detectDrift() logic. Unit test coverage is also currently thin relative to the e2e suite — the reconciler's happy path is covered under envtest, the individual drift-detection branches are not yet.

Case 02/ Linux · networking · automation/ infra-lab

One command rebuilds the entire host — firewall, VPN, TLS and monitoring

An internet-facing VPS provisioned entirely by Ansible: eight roles covering SSH hardening, an nftables edge firewall, WireGuard, a TLS-terminating reverse proxy, a CI runner and a Prometheus/Grafana stack.

View repository → Read the firewall ruleset →
Problem

A single public-facing host running several services is the point where hand-configuration stops being viable. Rules drift, nobody remembers which package was installed by hand, and rebuilding the box after an incident means rediscovering the setup from scratch.

Context

A Debian-family VPS serving infra-lab.space and its subdomains. Everything is expressed as Ansible roles, one per concern, applied in a fixed order by a single playbook. Secrets are held in Ansible Vault; the Cloudflare API credentials land on disk at mode 0600 inside a 0700 directory.

Architecture
# setup.yaml — order is the architecture
- hosts: main
  roles:
    - bootstrap            # sshd hardening, fail2ban, ip_forward, hostname
    - nftables             # edge firewall, default-drop forward chain
    - wireguard            # admin-plane VPN on udp/51820
    - postgres
    - nginx-reverse-proxy  # TLS termination + subdomain routing
    - certbot              # ACME DNS-01 + systemd renewal timer
    - gitlab-runner        # self-hosted CI executor (docker)
    - monitoring           # Prometheus + Grafana
setup.yaml

Nginx terminates TLS for the apex domain and reverse-proxies Grafana and Prometheus on their own subdomains, forwarding X-Real-IP, X-Forwarded-For and X-Forwarded-Proto. Port 80 exists only to issue a 301 to HTTPS. TLS is restricted to v1.2 and v1.3 with a shared session cache.

Technologies
AnsibleAnsible Vaultnftables WireGuardDocker ComposeNginx Certbot / ACME DNS-01Cloudflare DNS systemd timersPrometheusGrafana PostgreSQLfail2banGitLab Runner
Engineering decisions
  • nftables rather than iptables or ufw. One atomic ruleset loaded with nft -f, connection tracking expressed as a ct state vmap, and named counters on the SSH and WireGuard rules so "is anything actually hitting this rule?" is answerable without tcpdump.
  • Default-drop forwarding. The forward chain is policy drop with explicit accepts — the opposite of the permissive default most hosts ship with.
  • DNS-01 instead of HTTP-01. Certificates are issued through Cloudflare DNS, which allows wildcard certificates for the subdomains and removes the ACME dependency on inbound port 80 reaching a specific web root.
  • A systemd timer, not a cron entry. Renewal runs OnCalendar=monthly with Persistent=true, so a renewal missed while the host was off runs at next boot instead of being skipped, and RandomizedDelaySec=1h avoids hammering the ACME endpoint on the hour.
  • Hardening in the first role. SSH config is templated (key-based auth, no root password login), fail2ban is installed with a templated jail before anything else is exposed.
Difficult problems solved

1 — Containers went dark the moment the firewall landed. After the nftables role was applied, Docker containers started but couldn't reach anything. The input chain was fine and the host itself had connectivity, which localised the fault to forwarding rather than ingress: the forward chain's policy drop was discarding the bridge-to-host traffic Docker relies on, and only the WireGuard interface had been whitelisted. The fix was a single explicit rule for Docker's own interfaces — keeping the default-drop posture instead of relaxing the chain policy.

chain forward {
    type filter hook forward priority filter; policy drop;
    ct state vmap { invalid : drop, established : accept, related : accept }
    iifname "wg0" accept
+   iifname { "docker0", "veth*", "br-*" } accept
}
nftables/files/input.j2 · commit 54f3267

2 — Renewals succeeded; the served certificate never changed. The renewal unit exited 0 every month, yet Nginx kept presenting the old certificate. Two faults were stacked in the same template line: the reload command expanded to docker compose restart where the variable already contained docker, and it targeted a service named nginx while the Compose service was actually nginx-proxy. Certbot genuinely renewed the certificate — nothing ever reloaded the process holding it. This is the failure mode I look for hardest in other people's systems: the job reports success and the outcome never happens. The verification that matters is checking the served certificate, not the exit code.

certbot/templates/renew.sh.j2 · commit ab475dc
Result

A single ansible-playbook -i inventory/hosts setup.yaml reproduces the complete host: hardened SSH, firewall, VPN, database, TLS-terminating proxy, self-hosted CI runner and a monitoring stack — with certificates renewing on a timer that has been verified to actually reload the proxy.

Case 03/ AWS · Terraform · Helm · CI/CD/ microservices-deployment-eks-helm

A three-service platform on EKS, with a promotion path you can defend

Terraform-provisioned EKS running a UI, an auth service and a weather API — packaged as Helm charts and delivered by a GitLab pipeline that promotes the exact image it tested.

View repository → Read the Terraform →
Problem

Getting a multi-service application onto managed Kubernetes is the easy half. The hard half is making the infrastructure reproducible, giving stateful workloads real storage with correctly scoped cloud permissions, and building a release path where what reaches production is provably the artifact that passed staging.

Context

Three containerised services — a Node.js UI, a Go auth service backed by MySQL, and a weather API — deployed to an EKS cluster in eu-west-3, with a staging namespace and a production release gated behind manual approval.

Architecture
  • Network. A two-AZ VPC (10.0.0.0/16) with paired public and private /19 subnets. Subnets are tagged kubernetes.io/role/elb and internal-elb so AWS load balancer provisioning can discover them automatically.
  • Compute. The EKS node group is placed in the private subnets only, egressing through NAT — nodes are never directly addressable from the internet.
  • Identity. An IAM OIDC provider is created from the cluster's issuer, and the EBS CSI driver assumes a role via web identity restricted to exactly one subject: system:serviceaccount:kube-system:ebs-csi-controller-sa.
  • Storage. The EBS CSI driver is installed as a pinned EKS add-on (v1.21.0-eksbuild.1) wired to that role, giving MySQL real persistent volumes.
  • Packaging. One Helm chart per service, each with a Deployment, Service, Ingress, ServiceAccount, HPA and a helm test connection hook. The auth chart declares MySQL as a chart dependency.
Technologies
TerraformAWS EKSVPC IAM / OIDC / IRSAEBS CSIHelm GitLab CIDockerKubernetes RBAC HPAAlertmanagerVelero
Engineering decisions
  • IRSA over node instance profiles. Attaching AmazonEBSCSIDriverPolicy to the node role would grant every pod on every node the ability to manipulate EBS volumes. Federating through the cluster's OIDC provider and conditioning the trust policy on a single service-account subject scopes it to the one controller that needs it.
  • Immutable image tags. Staging deploys $CI_COMMIT_SHA. Nothing deploys latest.
  • Promotion by re-tagging, never rebuilding. The promote stage resolves the git tag back to its commit with git rev-list -n 1 $CI_COMMIT_TAG, pulls the image built from that SHA, and re-tags it as the release. The bytes that reach production are the bytes that ran in staging — a rebuild would silently pick up new base-image layers and dependency versions.
  • A human gate on production. The deploy stage is when: manual and fires only on tags.
  • A named cost trade-off. single_nat_gateway = true collapses NAT to one AZ. That is the right call for a lab and the wrong call for production, where the NAT gateway becomes a single-AZ dependency for all egress.
Hardest part

Getting stateful workloads working on EKS is a three-layer problem, and each layer fails in a way that looks like the others: the CSI driver add-on must exist, its service account must be annotated with a role, and that role's trust policy must name the exact OIDC subject. If the trust condition is wrong the pod comes up healthy and volume provisioning simply hangs — the PVC sits in Pending with no obvious cause until you read the CSI controller logs.

The second was designing promotion without rebuilds. Re-running a build on a tag is the obvious approach and it quietly breaks the guarantee that staging validated production's artifact; resolving tag → commit → existing image keeps that guarantee intact.

Implementation
# Trust policy scoped to exactly one service account
condition {
  test     = "StringEquals"
  variable = "${replace(aws_iam_openid_connect_provider.eks.url, "https://", "")}:sub"
  values   = ["system:serviceaccount:kube-system:ebs-csi-controller-sa"]
}
terraform/csi-driver-iam.tf 
# Promote the tested artifact — resolve tag to the commit that built it
TAGGED_HASH=`git rev-list -n 1 $CI_COMMIT_TAG`
docker pull $CI_REGISTRY_USER/weatherapp-ui:$TAGGED_HASH
docker tag  $CI_REGISTRY_USER/weatherapp-ui:$TAGGED_HASH \
            $CI_REGISTRY_USER/weatherapp-ui:$CI_COMMIT_TAG
.gitlab-ci.yml
Result

Infrastructure stands up from terraform apply. Merging to main builds, pushes and deploys SHA-tagged images to staging. Tagging a commit promotes those exact images and offers a manual production deploy. Backup and restore is covered by EBS volume snapshots and Velero.

Trade-off
Known limitation — stated deliberately The CI identity in this repository is bound to a Role granting '*' verbs on '*' resources. That is a lab shortcut, not a pattern I would ship: a deployment identity should hold only the verbs Helm actually needs on the resource types it actually manages, in the namespaces it owns. The pipeline also injects a base64 kubeconfig as a CI variable; on a production account I would replace that with short-lived credentials obtained through OIDC federation, so no long-lived cluster credential sits in CI at all.

04PhilosophyFive rules I actually apply, each drawn from the code above.

How I think about systems

These aren't slogans — each one is a decision you can find in the repositories on this page.

Reconcile, don't remember

State should be declared and continuously converged, not applied once and hoped about. That's why KubeGuard re-sweeps every five minutes instead of trusting its own event stream, and why every Ansible task in infra-lab is safe to run again tomorrow.

Exit code 0 is not success

A renewal job ran monthly and reported success for months while the proxy kept serving an expired-path certificate. Verification has to assert the observable outcome — the certificate actually served, the pod actually Ready — not the return code of the thing that was supposed to cause it.

Default deny, then justify each opening

Firewall chains start at policy drop. IAM trust policies name one service account, not a wildcard. Containers run non-root with all capabilities dropped. Every permission that exists should be traceable to a reason someone wrote down.

Promote artifacts, don't rebuild them

If production rebuilds from source, staging validated something else. Resolve the tag to the commit, promote the image that already exists, and keep the guarantee that what you tested is what you shipped.

Make the system explain itself

Status conditions, Kubernetes Events, correction annotations, named firewall counters. When something goes wrong at 3am, the system should be able to tell you what it did and when — without you reading its source code.

07ProcessThe order matters — I don't automate a system I haven't understood.

How I work

Four phases, in this order. On short engagements the first two may be all you need.

Phase 01

Read before writing

I start by mapping what you actually have — network path, permissions, deploy path, what breaks and how you find out. No changes in this phase. You get a written assessment with the risks ranked, and it's yours whether or not we continue.

Phase 02

Stabilise the sharp edges

Fix what is actively dangerous first: silent failures, over-broad credentials, missing backups, alerts nobody receives. Small, reversible changes, each one verified by its observable outcome rather than its exit code.

Phase 03

Codify it

Then the manual steps become Terraform, Ansible, Helm or a controller — whichever fits. The test is simple: can this environment be rebuilt from an empty account, and does the pipeline promote artifacts rather than rebuild them?

Phase 04

Hand it over properly

Your team owns the result: readable code, documented decisions including the trade-offs, and runbooks for the failure modes we actually hit. I'd rather leave you independent than indispensable to me.
